# 営業日報アプリ:変更して公開するまでの手順

CLAUDE.md の約束(日本語でやさしく・「作って」まで作らない・質問は1つ)は、そのまま守る。
この手順は、利用者が「作って」と言ったあとに使う。

## 1. 作り始める前

1. 作業用の枝を、最新の `main` から作り直す(前の合流の申請が合流済みのとき)。
   - `git fetch origin main && git checkout -B <作業用の枝> origin/main`
   - 作業用の枝に、まだ main に入っていない変更があるときは、作り直さず、その上に作る。
2. 画面の作りが分からないときは、`index.html` を読んで確かめる(推測で作らない)。
3. 保存データ(localStorage のキー)は、**消さない・名前を変えない**。新しく保存するときは、新しい名前を使い、CLAUDE.md の「保存データ」に書き足す。
4. `index.html`(元のアプリ)は、なるべく変えない。直すときは、`container.js` で包む(`window.xxx = function(){ 元の関数(); 足す処理 }`)。

## 2. 作ったあとの確認(全部が通るまで、送らない)

1. 文法の確認: `node --check container.js`
2. 自動確認: `cd nippo-tests && python3 run_tests.py`(約2〜3分)。最後に `ALL PASS` が出れば合格。
   - 新しい動きの確認は、`extra_tests.js` の末尾に、`// ---- 番号) …` で区切って足す。
   - 決まりが変わって古い確認が合わなくなったときは、`post_build7.py` に置き換えを書き足す(または、その確認が `extra_tests.js` にあれば、そこを直す)。**確認を消して合格させない。**
   - 確認用の画面(`harness3.html` を元に `harness4.html` を作る)に部品が足りないときは、`post_build7.py` の末尾で `harness4.html` に足す(本物の `index.html` と同じ部品・同じ働きにする)。
   - 天気の確認3つ(「row 天気」など)は、日本時間の0時すぎに回すと落ちることがある(確認側の時刻の扱い)。そのときは、`main` の container.js でも同じに落ちるかを確かめてから、利用者にそう伝える。
3. 見た目の確認: `python3 -m http.server` で開き、Playwright(`/opt/node22/lib/node_modules/playwright`、幅375px)で画面写真を撮って見る。写真は利用者にも送る。
4. 自分の変更を読み直す(古いコメント・使わなくなった部品・文言の括弧が全角になっていないか)。

## 3. 書き足し・版上げ

1. `sw.js` の `CACHE` の版を1つ上げる(例: `nippo-cache-v8` → `v9`)。CLAUDE.md の「sw.js」と「7. 変更するときの注意」の版の数字も合わせる。
2. CLAUDE.md の「4. 仕様」に、決まったこと(数字・色・動き)を書き足す。古くなった記述は直す。テスト用に公開した `window.ctXxx` は、「container.js(追加機能)」の一覧に足す。
3. 手順そのものが変わったときは、この SKILL.md を直す。

## 4. テスト用のページに公開(ふつうは、ここまで)

1. 作業用の枝にコミットして送る(コミットの文は日本語。変えたこと・確認の項目数を書く)。
2. テスト用のページ: `https://raw.githack.com/taiqim-gif/BCP-Nippo1/<作業用の枝>/index.html`
   - いつものアプリとはデータが別(最初は空)。ホーム画面に追加しないよう伝える。
   - 新しい版が出ないときは、数分待って読み込み直すよう伝える。
3. 利用者が「テストで」「テストページに」と言ったときは、**main には入れない**。

## 5. main に入れる(利用者が「main に入れて」「main に作って」と言ったときだけ)

1. 作業用の枝から `main` への合流の申請を作り、合流する。
2. `main` に入ったことを確かめる(`git show origin/main:sw.js` の版など)。
3. 利用者に、iPhone で新しい版にする手順を伝える:
   1. データ画面の「バックアップ保存」を押す。
   2. アプリを完全に閉じて、1〜2分待ってから、もう一度開く。
   3. 新しい版だと分かる目印(今回変えた画面)を1つ伝える。

## 6. 報告のしかた(毎回)

次の順で、やさしく、番号を付けて書く。

1. **変えたところ**(決めたとおりにしなかったところがあれば、理由といっしょに、はっきり書く)
2. **テストの結果**(項目数と ALL PASS か。落ちたものがあれば、正直に、その理由)
3. **実機(iPhone)で見てほしい点**(パソコンでは確かめられない、見た目・指の操作・キーボードの動き)
4. どこに入れたか(テスト用のページか、main か)と、次にしてほしいこと

利用者が「終わったら知らせて」と言ったときは、通知(PushNotification)を送る(パソコンの音は鳴らせないことを伝える)。
