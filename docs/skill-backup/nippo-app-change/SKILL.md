# 営業日報アプリの改修の進め方

このアプリは、会話をまたいで何十回も改修してきました。手戻りの多くは、次の3つが原因でした。

- 元のファイルがないまま作り直した
- 言葉の意味を決め打ちした（例：内容区分を「単一選択」と取り違えた）
- 新しい機能を足したとき、既存の機能とのつながりを見落とした（例：全データ削除でTODOが消えない、メールから位置情報が消えた）

このスキルは、この3つを防ぐための手順です。ユーザーは日本語だけで話します。専門用語を避け、短く、順を追って説明してください。

## 最初にやること

1. `references/project-state.md` を読み、現在の仕様と決定事項をつかむ。
2. アプリの最新ファイルを探す。`/mnt/user-data/outputs/` と `/mnt/user-data/uploads/` を見る。作業用の `/home/claude/` は会話ごとに消えるので、見つかったファイルを作業場所へコピーして使う。
3. 最新のファイルが見つからないときは、メモリや記憶から作り直さない。ユーザーにファイルの添付を頼む。

## 依頼の分け方

**小さな修正は、確認せずにすぐ直す。** 文言、ボタンの名前や位置、色、並び順、既存機能の軽い変更が当たります。

**大きな依頼は、作る前に要件を確認する。** 次のどれかに当たるときです。

- 保存するデータの形が変わる
- メール、暗号化、ファイル、サーバーなど、外とつながる
- 安全性や個人情報に関わる
- 新しい画面やタブが増える
- 言い方が曖昧で、解釈で結果が大きく変わる

確認のやり方は次のとおりです。

- 質問は、選択式（`ask_user_input_v0`）で、1回に3問までにする。
- 案がいくつかあるときは、それぞれの良い点と弱点を短く並べる。
- 決まったことを整理して見せ、ユーザーが「作って」と言うまで、コードは作らない。
- ユーザーが「まだ作らない」「打ち合わせしてから」と言ったときは、必ず守る。

## 言葉の確認

次のような言葉は、決め打ちしない。意味が結果に響くなら、先に聞く。響かないなら、どう解釈したかを返信に書いて作る。

- 入力の部品：トグル、スピナー、ステッパー、ダイヤル、コンボボックス、ボタン
- 「一覧」「履歴」「削除」が、どのデータを指すか
- 「選択」が、1つだけ選ぶ意味か、入力を助ける意味か
- 「送信データ」が、メールか、スマホ内のデータか

## 作るとき

- アプリは1つのHTMLファイル。既存のファイルを部分的に直す（`str_replace` やPythonでの置換）。全体を書き直さない。
- 保存の名前（`meetingLogs`、`dailyVehicleInfo`、`todoItems`、`customerLists`、`appLastOpenDate`）は変えない。形を変えるときは、古い形式を自動で引き継ぐ処理を入れる。
- 日報メールに行を足すときは、既存の行の並びを変えず、ブロックの末尾に足す。受け取り側の取り込み処理を壊さないため。
- 暗号のコード（`/* ===CRYPTO-BEGIN=== */` から `CRYPTO-END` まで）は、アプリとツールで同じ文字列にする。片方を直したら、もう片方も同じに直す。
- 新しい機能を足すときは、`references/verification.md` の「連動チェック」を必ず通す。

## 渡す前の確認

`references/verification.md` の手順で、動作確認をしてから渡す。確認できないこと（iPhone実機でのドラッグやメールの起動など）は、できていないと正直に書く。調べた事実を述べるときは、出典を示す。「消えません」「安全です」のような言い切りは、確かめた範囲だけにする。

## 渡し方

1. 完成したファイルを `/mnt/user-data/outputs/` に置き、`present_files` で渡す。
2. 返信は、次の順に短く書く。
   - 何を変えたか
   - 注意点と影響（メールの形、データ、他の画面）
   - 確認できていないこと
   - 決めてほしいことがあれば、1つだけ
3. 仕様が変わったら、仕様書・要件定義書・取扱説明書も更新する。文書は、すでにある Claude Docs を更新し、作り直さない（IDは `references/project-state.md`）。
4. 依頼のやりとりが終わったら、返信の最後に、記録案を1行で付ける（下の書式）。

## 記録案の書式（毎回、最後に1行）

ユーザーは、依頼が終わるたびに往復数と手戻りの理由を記録し、たまったら分析する。次の形で1行にする。

`記録案：往復○回／手戻り：（理由の記号）理由を10文字ほどで`

理由の記号は次のとおり。

| 記号 | 意味 |
| --- | --- |
| A | 情報不足（ファイルや前提を聞いていなかった） |
| B | 要件変更（途中で決めたことが変わった） |
| C | 範囲が大きい（一度に頼む量が多かった） |
| D | 完成形が未共有（最終的な姿が伝わっていなかった） |

例：`記録案：往復3回／手戻り：A 元ファイルがなかった`
手戻りがなければ、`手戻り：なし` と書く。往復数は、その依頼について、ユーザーが送ったメッセージの数で数える。決められないときは、概数で書き、概数だと添える。
